|---|---|

| `cursor/no-rollback` | 回退抛 `RangeError` 且零副作用 |
| `cursor/not-past-log-end` | 越过日志末尾抛 `RangeError` 且游标不动；空流上任何 advance 都抛 |

| `fuzz/model-equivalence` | 固定种子随机交错（append / 陈旧 CAS / read 窗口 / 合法前移 / 非法游标）对影子模型逐步比对；默认 3 种子 × 60 步 |

## 关键决策（为什么这么写）

1. **不动既有 `log-cursors.property.test.mjs`。** 就绪评估里我原写"既有 property 测试改为一行调用"——**那个想法是错的**：它虽保留全部断言，但会修改既有测试文件，直接撞 rules.md §技术与目录 4 的兼容门（"既有测试一行不许改"）。改判后的分工也更干净：既有 property 测试考的是**内核 + 内存实现 + delivery 投递层**（它 import 了 `createDelivery`），新套件考的是**任意适配器对 logStore 四方法的义务**——scope 不同，不是重复。代价是两处都有"seq 连续/游标只进"的模型断言；这个重复我认，换来兼容门零风险。
2. **零 import。** 没有引 `node:assert`（纯度门是允许 `node:` 内建的，不是被挡）：套件要发给消费方在任意 runner 里跑，引了 `node:assert` 就把这个文件绑死在 Node 上，破坏全库"零依赖 + 浏览器可跑"的一致性。代价是自写 12 行 `must/mustEqual/mustThrow`，深比较走 `JSON.stringify`——够用，且失败信息带检查名比裸 AssertionError 更有指向。
3. **抛错而不是返回报告。** 不做 `{ok:false, failures:[]}` 那套：消费方要的是"我的适配器过没过"，第一条违约就该炸，且天然适配任何测试框架。收集式报告是没人要的分支。
4. **`seeds`/`steps` 两个旋钮保留。** 内存实现下 3×60 步是毫秒级，但真 DB 适配器（每步一次事务 + 全量 read）会慢一个量级——不给旋钮，消费方只能整套不跑。这是真实硬件差异，不是可配置性洁癖。
5. **每项检查取一个全新 store**（`createStore()` 每次必须返回全新空存储，已写进 JSDoc 与契约草案）：否则前一项的残留数据会让后一项的 CAS 期望漂移，坏适配器反而更容易蒙混。
6. **模糊检查里的"回退攻击"目标限定在 `[1, cur-1]`。** 首跑被自己抓到一次真问题：原式会生成 `seq=0`，而内存参考实现对 `seq=0` 抛 `TypeError`（入参非法）而非 `RangeError`（游标违规）——契约把这两类错误分得很清（编程错误 vs 游标违规），套件不该要求参考实现不具备的行为。**这是套件第一次发挥作用，抓的是它自己。**
7. **不新增 `exports` 映射**：仓根 `package.json` 已有 `"./session/*"`，消费方直接 `@aimergent/realtime-core/session/logstore-conformance` 即可，零配置改动。

> 6. **`pull` 不动游标**：at-least-once，未 `ack` 必重投，消费侧逻辑需幂等。

## R1 · 并发 CAS 漏检（共同 P1，最重）

**他们对，我错在哪**：我把"CAS"当成了一个**值的比较**去验（串行 stale/ahead 两侧），而 CAS 的本质是**比较与提交之间不得有窗口**。两位 reviewer 各自构造的坏适配器（`review/reviewcode/session/…-opencode.mjs:222` 的 `racyCASStore`、`review/reviewcode/backend/session/…-codex.mjs:153` 的 `createInterleavingCasStore`）串行语义**逐字正确**、9/9 全过，但在 `Promise.all` 同 `expectedLastSeq` 下两路都 fulfilled、日志只留一条——**已确认的写入被静默覆盖**。这正是 `logstore-conformance.js` 文件头自称要挡的失败类，也是 contract I7 的承诺面。套件漏了它，"跑通即达标"就是假的。

**修法**：新增第 10 项检查 **`append/cas-concurrent`**（`code/backend/src/session/logstore-conformance.js`，排在 `append/cas-conflict` 之后）：同一新流上三路 `append(s, 0, …)`，断言**恰好一个 fulfilled、其余全 `ConflictError`**，日志恰好多出胜者那一批（seq `[1]`、不重不丢），胜者返回的 `lastSeq` 与日志实际长度一致，且竞争后续写仍能接着真实 `lastSeq` 连续编号。

**怎么做到确定性（不依赖真并发时序、零定时器）**：三路 append 用 `(async () => store.append(...))()` **先全部发出**——每路同步执行到自己的第一个 `await` 为止——再 `Promise.allSettled` 统一收割。三类适配器的结果都由 JS 微任务语义决定，不由墙钟决定：

| 适配器 | 发生什么 | 结果 |
|---|---|---|
| 同步适配器（内存参考实现） | 第一路在调用时就写完；后两路**调用时**已看到新 lastSeq | 1 胜 2 冲突 ✅ |
| 正确的异步适配器（事务 / 唯一约束 / 内部串行队列） | 比较与提交原子，或后来者重读真实 lastSeq | 1 胜 2 冲突 ✅ |
| TOCTOU 适配器（读快照 → 让出 → 按陈旧快照提交） | 三路都在任何一路提交前读到同一快照 | 3 路全"成功" ❌ 被抓 |

因此结论**与调度顺序无关**：任何真正实现 CAS 的适配器都只能有一个胜者，而任何"先读后写"的适配器都会让多路同时通过。新增测试 `logstore-conformance · 并发检查是确定性的` 连跑两次断言违约信息**逐字相同**，把这条性质本身钉死。

### 更正 ①（`contract.md:238` 消费方义务第 4 条）—— **当前表述与实现相反，必须整条替换**

**我错了，且错在源头**：这条是我在就绪评估 B6 里写的"同 group 谁先 pull 谁拿走"，CFO 照抄进契约。**实测证伪**（`code/backend/src/session/delivery.js:78-88`：`pull` 只 `read` + 记 `pulledHigh`，**不动游标**）：

```
同 group 连续两次 pull:  [1,2]  [1,2]   游标=0      ← 两次都拿到同一批，不是竞争
其中一方 ack(2) 之后再 pull:  []        游标=2      ← 共享游标被推进，另一方从此看不到 ≤2
另一个 group 从头读:    [1,2,3]                     ← 换 group 才有独立进度
```

**正确表述（建议逐字替换第 4 条）**：

> 4. **同一 `group` 共享一枚游标——重复投递，不是竞争消费**：`pull` 不动游标，所以同 group 的多个订阅者（同一用户的多个标签页、多个 worker 实例）**各自都会收到同一批未确认事件**（at-least-once 的自然结果，消费逻辑必须幂等）。真正的危险在 **`ack`**：任一订阅者的前缀确认会把**全组共享**的游标前移，其他订阅者从此再也见不到 `≤seq` 的事件——**哪怕它们还没处理**。三条出路按页面性质选：①同 group 但只让一个"权威"实例 `ack`，其余只读（最省）；②每个订阅者一个独立 group，各自游标互不干扰（游标记录随订阅者增长，回收归消费方——端口不提供删除游标的方法）；③用 `createPollRegistry()` + `longPoll` 的 `registry`/`key` 顶替，只保留最后一个连接（旧连接收 `superseded`）。**必须显式选一个**——默认行为是"都收到、但谁 ack 谁就替全组前移游标"。

（顺带：这也修掉 Codex P1-2 指出的"同节自相矛盾"——第 4 条与第 6 条"`pull` 不动游标"原本互斥。）
